# DriveGuard AI 文档协作与同步规范

## 1. 目的

本规范用于让代码、模型、数据库、API 和文档在持续迭代中保持有效对齐。它是一套轻量评审流程：要求检查影响并在契约变化时同步文档，但不会把与变更无关的文案调整设为开发阻塞项。

## 2. 基本原则

1. 代码和文档共同描述系统：代码说明当前实现，Spec 和接口文档说明预期行为。
2. 每次变更都应做一次文档影响判断，判断结果可以是“需要更新”或“已检查，无需更新”。
3. 外部行为或跨层契约发生变化时，文档最好与代码在同一变更中更新，避免长期漂移。
4. 发现历史偏差时先确认正确行为，再修代码或文档；不得为了“对齐”而盲目让文档追随错误实现。
5. 未实现的设计必须标记为设计基线，不能写成已上线能力。

## 3. 需要检查文档影响的变更

| 代码/配置变化 | 应检查的文档 |
| --- | --- |
| 新增或修改业务行为 | Requirements、Project Spec、测试策略 |
| 模块边界、数据流、部署变化 | 架构设计、相关 ADR |
| 表、字段、约束、索引、保留策略变化 | 数据库设计、API schema、迁移说明 |
| REST 路径、字段、状态码、权限变化 | API 设计、OpenAPI、Spec Scenario、前端类型 |
| WebSocket 消息或重连策略变化 | API 设计、前端类型、契约测试 |
| 模型输入特征、标签、版本或指标变化 | 需求、架构、Spec、测试策略 |
| YOLO/MediaPipe/手物关联、模型组合变化 | 完整多专家设计、TCN 子设计、训练职责、部署、模型 runtime 契约 |
| 前后端选型、预览、IPC 或平台镜像变化 | 应用技术选型、部署、API/OpenAPI、隐私场景 |
| 配置键、默认值、生效方式变化 | 需求、API、数据库、部署说明 |
| 性能、安全或隐私目标变化 | Requirements、Architecture、Test Strategy |
| 纯内部重构且契约不变 | 通常无需改正文，记录检查结论即可 |

## 4. 迭代流程

### 4.1 开始开发前

- 根据变更范围定位相关 `FR/NFR/REQ/API` 编号。
- 检查文档中的当前行为、边界和待确认项是否仍适用。
- 若需求本身改变，先更新或提出 Spec 变化，再实现对应代码。

### 4.2 开发过程中

- 字段和枚举优先从共享 schema 生成或复用，减少手工重复定义。
- 数据库、Pydantic/OpenAPI、WebSocket 和 TypeScript 中的同一概念保持统一名称与语义。
- 新发现的约束、失败模式或部署差异及时写入相关章节，不等到项目结束集中补写。

### 4.3 评审时

变更说明填写以下最小信息：

```markdown
## 文档影响

- 影响判断：需要更新 / 已检查，无需更新
- 关联需求或 Spec：REQ-007、API-003
- 已同步文件：docs/api/API_DESIGN.md、docs/api/openapi.yaml
- 未同步项及原因：无
- 验证：OpenAPI 解析通过，契约测试通过
```

评审者重点核对：

- 变更行为是否仍符合 Scenario。
- 对外字段、错误码、权限和版本是否与文档一致。
- migration、Repository、API schema 与测试是否同源。
- “无需更新”是否确实没有契约影响。

### 4.4 合并后

- 自动发布文档或契约工件的项目，应确认生成步骤成功。
- 如果因合理原因不能在同一变更完成同步，必须创建明确关联项，注明负责人、范围和验证方式；该例外不应成为常态。

## 5. 严格程度分级

| 等级 | 场景 | 处理 |
| --- | --- | --- |
| 必须同步 | 公共 API 破坏性变化、数据库 schema、隐私/安全行为、风险等级语义 | 同一变更同步文档、契约与迁移/兼容说明 |
| 应同步 | 新功能、配置、模型特征、可观测指标、部署变化 | 优先同一变更更新；延期需关联说明 |
| 检查即可 | 重命名局部变量、格式化、无行为变化的内部重构 | 记录“已检查，无需更新” |

这里的“必须同步”针对受影响的契约文档，不要求修改所有文档，也不因无关的排版或措辞差异阻断代码迭代。

## 6. 冲突裁决

当代码、测试和文档互相冲突时：

1. 用用户需求、已确认 Spec 和可复现测试确定预期行为。
2. 若实现不符合预期，修正实现并保留回归测试。
3. 若文档过时，修正文档并说明变化来源。
4. 若需求已变化，先更新 Spec/决策记录，再同步实现与测试。
5. 无法确定时标记为未对齐，不把任一方未经确认地视为真相。

## 7. 版本和状态

- 文档版本采用语义化版本的简化形式：重大契约变化升主版本，兼容新增升次版本，文字澄清升修订版本。
- 文档头部注明 `设计基线/已实现/已验证/已废弃` 等状态。
- OpenAPI 的 `info.version` 表示 API 契约版本，不等同于服务构建版本。
- 架构决策需记录反选理由、接受代价和重新评估条件。

## 8. 自动化建议

后续仓库具备代码后，可逐步加入：

- YAML/OpenAPI 语法解析。
- FastAPI 生成 OpenAPI 与仓库契约的结构 diff。
- 数据库 migration 与文档化 schema 的差异检查。
- Python/TypeScript 共享枚举生成或契约测试。
- Markdown 内链和标题锚点检查。
- `REQ-*` 到测试标记的追溯完整性检查。

自动化的目标是快速发现漂移，不替代对业务语义的人工评审。

## 9. 文档所有权

| 文档 | 建议主要维护者 | 必要协作者 |
| --- | --- | --- |
| Requirements / Spec | 产品或技术负责人 | 算法、开发、测试 |
| Architecture | 技术负责人 | 算法、后端、前端、部署 |
| Database | 后端负责人 | 测试、数据/隐私负责人 |
| API / OpenAPI | 后端负责人 | 前端、测试 |
| Test Strategy | 测试负责人 | 算法、开发、部署 |
| Governance | 技术负责人 | 全体贡献者 |
| 训练协议、模型结构、实验报告、权重模型卡 | 算法工程师 shadow | 推理集成维护者、项目负责人 |

shadow 的具体工作包、GPU/昇腾 NPU 双平台交付与数据/权重 Git 策略见[训练职责约定](../training/TRAINING_CHARTER.md)。`model` 为训练开发分支；署名用于职责和文档，不改写 Git 全局身份。

## 10. 完成定义

一次代码迭代在文档维度达到完成的条件是：

- 已做文档影响判断。
- 受影响的契约文档已同步，或存在明确、可追踪的延期说明。
- 实现、测试与文档没有已知但未披露的冲突。
- 新增行为可追溯到 Requirement/Scenario 或有清晰的需求来源。
