| 项目 | 内容 |
| --- | --- |

| 文档版本 | 0.3.0（2026-09-19，部署便利与多平台兼容细化） |

## 2. 背景与问题

传统单帧目标检测加固定阈值的方案难以区分正常眨眼与持续闭眼、物体出现与真实交互，也容易因驾驶员个体差异产生误报。DriveGuard AI 通过多模型感知、连续时序理解和风险融合，在车端持续评估疲劳、分心与操作风险。

## 3. 产品目标

系统应做到：

1. 在车辆本地实时处理摄像头视频，网络中断不影响核心检测和本地告警。
2. 对疲劳、手机使用、饮水、视觉分心等行为进行连续而非单帧判断。
3. 输出 `SAFE`、`WARNING`、`DANGER` 三级风险、主要风险来源及置信度。
4. 保留可查询的危险事件元数据，支持实时监控、历史查询和统计分析。
5. 为桌面 GPU 和 NVIDIA Jetson Orin 系列提供一致的模型部署路径。

工程优先级（2026-09-19用户确认）：部署便利、多平台兼容、效果和维护成本优先，不要求论文写作角度创新。共享PyTorch模型/数据语义，保留CPU参考和GPU/昇腾训练入口；平台环境独立验证，不要求同一二进制或虚拟环境跨平台运行。轻量关系门控是可选升级，实测无收益则保留现有TCN；ONNX/TensorRT按实际目标选择，不强制每个平台启用。详见[融合设计](../architecture/RELATION_GATED_FUSION.md)与[部署矩阵](../deployment/DEPLOYMENT_DESIGN.md)。

## 4. 范围

### 4.1 MVP 范围

- 单车、单驾驶员、单车内摄像头。
- 视频采集、基础画面质量检查和实时帧处理。
- 手机、瓶/杯等交互物体检测。
- 驾驶员手部归属与手—物体邻近/持续交互证据，用于区分物体出现与实际行为。
- 人脸关键点、EAR、MAR、PERCLOS、眨眼、闭眼时长与头部姿态特征。
- 3–5 秒滑动窗口和 TCN 时序行为识别。
- 疲劳、手机使用、饮水、分心风险及三级综合风险融合。
- 本地声音/视觉告警。
- FastAPI REST API、WebSocket 实时推送、React Dashboard。
- React + TypeScript + Vite + ECharts 实时指标、曲线与历史统计；独立鉴权视频预览默认关闭。
- SQLite 事件、配置和模型版本元数据持久化。
- YOLO/TCN 的 PyTorch → ONNX → ONNX Runtime/TensorRT 部署链路，MediaPipe 独立验证运行时；Docker/Ubuntu/Jetson 部署。

### 4.2 后续范围

- 独立 Gaze 区域预测、Eyes-Off-Road、完整手部动作/Hands-Off-Wheel；首版所需手物交互证据不在延期范围内。
- 多摄像头融合、多驾驶员/多车辆云端管理。
- Gated/MLP/Reliability-Aware Fusion、Video Transformer。
- PostgreSQL、多租户、远程设备管理。

### 4.3 明确不在 MVP 范围

- 自动控制车辆或替代驾驶员决策。
- 将 DMS 输出作为医疗诊断结论。
- 默认上传或长期保存原始车内视频。
- 依赖云服务完成核心告警。
- 在当前规划阶段承诺特定法规认证。

## 5. 用户与角色

| 角色 | 目标 | 典型操作 |
| --- | --- | --- |
| 驾驶员 | 及时获知风险且减少无意义告警 | 接收本地告警、继续在断网状态使用系统 |
| 监控人员 | 掌握当前状态和历史事件 | 查看实时指标、事件列表、统计趋势 |
| 系统管理员 | 管理设备参数与模型 | 修改摄像头/告警/阈值配置、查看模型版本 |
| 算法工程师 shadow | 训练、评估和公开交付权重 | 数据切分、JSON 超参数、模型结构、GPU/昇腾 NPU 双入口、checkpoint、实验记录、推理交接 |
| 维护人员 | 部署、诊断和恢复服务 | 健康检查、日志检查、回滚模型与配置 |

## 6. 功能需求

### FR-001 视频采集

- 系统应支持 OpenCV 或 GStreamer 摄像头输入。
- 采集异常时应产生可诊断状态，不得让后端或 Dashboard 无提示地显示旧数据。
- 恢复摄像头后应自动恢复推理或给出明确的人工恢复指引。

### FR-002 帧级感知

- 系统应通过 YOLO 检测手机、瓶、杯；香烟等新增类别在具备标注和评估后配置启用，不默认声称预训练模型支持。
- 系统应通过 Face Landmarker 获取面部关键点并计算 EAR、MAR、PERCLOS、眨眼与闭眼时长。
- 系统应输出 Yaw、Pitch、Roll 头部姿态及每项特征的有效性状态。
- 人脸不可见、关键点质量不足或模型异常时，特征不得伪造为正常值。
- 系统应关联驾驶员手部与物体，输出空间/持续交互证据；手不可见或副驾驶归属不明时标记无效。头姿不得冒充独立 gaze 预测，具体边界见[完整多专家模型](../architecture/MULTI_EXPERT_DESIGN.md)。

### FR-003 时序行为理解

- 系统应将连续帧级特征组成可配置的 3–5 秒滑动窗口。
- 系统应区分瞬时眨眼与持续闭眼、物体短暂出现与持续交互。
- 缺失帧或低质量特征应被显式标记并按定义的降级策略处理。

### FR-004 风险识别与融合

- TCN 应输出疲劳、手机使用、饮水和分心概率。
- 四类行为允许同时成立；本阶段分心目标细化为视觉分心，不等同于综合风险。Gaze/Drows/Dist 来源不能直接充当行为标签，注视后视镜不自动等同于危险分心。
- Risk Fusion 应结合概率、持续时间和输入可靠性输出三级风险。
- 输出应包含主风险类型、各风险分数、总风险等级、置信度和生成时间。
- 首版采用可配置规则融合；升级为学习型融合时不得改变对外契约语义。

### FR-005 本地告警

- 达到告警条件时，系统应在边缘设备本地触发声音或视觉提示。
- 告警应支持冷却时间、升级、恢复和重复抑制。
- Dashboard 或网络故障不得阻止本地告警。

### FR-006 危险事件管理

- 风险进入可记录状态后应创建事件；持续同类风险应聚合为单个事件并更新持续时间。
- 事件应记录类型、开始/结束时间、置信度、持续时间、最高风险等级、模型版本和可选摘要。
- 默认只保存事件元数据；视频片段保存必须由配置显式开启。
- 监控人员应能分页、筛选和查看事件详情。

### FR-007 实时监控

- Dashboard 应显示连接状态、实时风险、EAR、MAR、PERCLOS、头部姿态和检测结果。
- 实时数据通过 WebSocket 推送，客户端断线后应支持指数退避重连。
- 每条实时消息应有协议版本、会话 ID、序列号和服务端时间戳。
- 视频通过独立 MJPEG HTTP 通道，不塞入 JSON WebSocket；默认关闭、开启后仍需鉴权、只在内存预览。推理/状态/预览帧率分别记录，预览不是录像授权。
- 预热、无有效快照、旧数据和断连时必须显示不可用/过期；不能将缺失值显示成零风险。

### FR-008 统计分析

- 系统应按时间范围统计危险事件数、风险类型分布、持续时间和风险趋势。
- 无数据时返回空统计结果，不得以服务异常代替。

### FR-009 系统配置

- 管理员应能读取和更新摄像头、告警、风险阈值、模型路径与模型版本配置。
- 更新应校验类型和范围；无效配置不得覆盖当前有效值。
- 影响运行时的配置变更应返回是否立即生效、需重启或被拒绝。

### FR-010 模型与运行状态

- 系统应公开当前模型名称、版本、运行时和加载状态。
- 系统应公开摄像头、推理管线、数据库、WebSocket 和资源使用状态。
- 模型加载失败时应保留明确错误并进入安全降级状态。

### FR-011 训练与评估

- DMD 数据集必须按驾驶员主体进行训练、验证和测试划分，主体不得跨集合。
- 评估必须至少报告 Precision、Recall、F1、False Alarm/Hour、Detection Delay 和 FPS。
- 模型工件应记录训练配置、数据版本、指标、导出格式和校验值。
- shadow 负责模型训练工程，具体分工与交付见[训练职责约定](../training/TRAINING_CHARTER.md)。
- 数据根目录应可按本地/服务器覆盖；原始数据、派生特征和下载缓存从 Git 排除。
- 同一模型提供 GPU 与华为昇腾 NPU 两套训练入口，共用模型和训练契约；服务器软件版本确定后分别实测。
- 正式训练 checkpoint 权重必须公开交付，附模型卡、可复现配置与校验和；第三方数据与权重许可待核实项必须显式记录。

训练设计补充：不同子集缺少某类标注时，该类必须标记未知而非负例；训练损失与评估均排除未知项。同一驾驶员在不同子集、录制和摄像头视角中归属同一划分。完整方案见[多专家模型设计](../architecture/MULTI_EXPERT_DESIGN.md)，时序细节见 [TCN 子模型](../training/MODEL_DESIGN.md)。YOLO 另需检测框标注，不以行为区间代替 bbox。当前下载安排为 Gaze 两个分片、Drows 一个分片、Dist 一个分片，尚未核对覆盖，四任务能力不能仅凭分片数验收；本轮数据任务继续暂停。

## 7. 非功能需求

### NFR-001 实时性

- 目标处理速度为持续 `≥ 25 FPS`；报告必须注明硬件、分辨率、模型和批大小。
- 告警检测延迟应按风险类型单独测量；具体阈值在模型基准完成后固化。
- REST 列表接口在本机 10 万条事件数据、默认分页条件下的 P95 目标为 `< 300 ms`，该值属于工程设计目标，需实现后验证。

### NFR-002 可用性与降级

- 网络断开时，本地采集、推理和告警应继续工作。
- 单个专家模型失败时，风险结果应标记可靠性下降，不得把缺失输入当作安全。
- 服务重启后应恢复持久化配置并避免重复写入同一已完成事件。

### NFR-003 隐私

- 默认不上传原始视频，默认不持久化完整帧。
- 日志、API 和数据库不得保存凭证或无必要的人脸图像数据。
- 启用事件视频片段时必须配置保存目录、保留期、磁盘上限和访问权限。

### NFR-004 安全

- 除健康检查外的管理接口应支持 Bearer Token；生产部署必须启用鉴权。
- 所有外部输入应进行类型、范围和长度校验。
- 错误响应不得暴露堆栈、主机绝对路径或凭证。

### NFR-005 可维护性

- 感知、特征、时序、融合、业务服务、API 和 UI 应保持清晰边界。
- 模型输出和 API 消息必须通过版本化数据契约交互。
- 配置、模型、数据库和 API 变更应具备迁移与回滚说明。

### NFR-006 可观测性

- 日志应包含时间、级别、组件、事件/会话关联 ID 和机器可读错误码。
- 应记录 FPS、推理耗时、队列积压、WebSocket 客户端数、事件写入失败和模型状态指标。

## 8. 核心业务规则

1. 单帧物体检测结果不是行为结论；行为结论必须来自时序判断或显式降级规则。
2. 输入质量不足时，系统输出 `unknown/degraded` 质量状态，不得默认输出 `SAFE`。
3. 风险等级只允许 `SAFE`、`WARNING`、`DANGER`，数据库与 API 统一使用大写枚举。
4. 时间统一以 UTC 存储与传输，UI 按用户时区展示。
5. 风险阈值和告警延迟由配置提供；默认值在实验验证前属于待确认参数。

## 9. 验收标准

| 编号 | 验收内容 | 证据 |
| --- | --- | --- |
| AC-001 | 摄像头连续输入时完成感知、时序、融合和本地告警闭环 | E2E 录像回放测试与日志 |
| AC-002 | 网络断开后核心检测和本地告警继续运行 | 断网测试 |
| AC-003 | 正常眨眼不会被简单等同于长闭眼危险事件 | 标注视频回放与 Scenario 测试 |
| AC-004 | 事件可以通过 REST 分页筛选，实时状态可通过 WebSocket 接收 | API/WS 集成测试 |
| AC-005 | 同一硬件条件下持续处理速度达到 25 FPS 目标或明确记录差距 | 基准测试报告 |
| AC-006 | 原始视频默认不持久化，事件元数据字段完整 | 配置检查、数据库断言 |
| AC-007 | DMD 切分不存在驾驶员主体泄漏 | 数据集划分审计脚本输出 |
| AC-008 | 代码迭代涉及契约变化时，相应文档和可机读接口同步更新 | 变更评审记录与一致性检查 |
| AC-009 | 背景手机/静置水杯与驾驶员持续交互区分，手部缺失正确降级 | 手物交互反例、消融与录像回放 |
| AC-010 | 受鉴权实时预览默认关闭，预览/API 故障不停止本地告警 | 预览契约、隐私与故障测试 |
