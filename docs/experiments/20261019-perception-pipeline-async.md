# 感知管线耗时剖析与检测器异步化

2026-10-19 · `model` 分支 · 复现脚本：`scripts/local/profile_perception.py`、
`scripts/local/compare_windows.py`

范围：定位单帧 250 ms 的真实构成，把最慢的协作者移出关键路径，并量化这样做的
精度代价。不涉及训练、阈值调整、NPU 或应用层。

## 1. 为什么先剖析再改

上一轮只掌握端到端数字（`processing_ms` p50 250 ms），而曾记录的分阶段表
（MediaPipe 17 ms、eye 4 ms）与它不自洽。在不知道 250 ms 由谁构成的情况下做优化
等于碰运气，所以先测量。

## 2. 方法

`CameraPerception` 是真实产品类。剖析脚本不修改产品代码，而是把它的四个协作者
包一层计时器后直接调用 `frame()`：

| 被计时对象 | 说明 |
|---|---|
| `perception_worker.decode_jpeg` | JPEG 解码（1280×720） |
| `detector.predict` | 到检测器进程的完整 HTTP 往返 |
| `landmarks.predict` | MediaPipe face + hands |
| `locator.step` | 第二个 face 图（头部裁剪）上的眼位 |
| `extractor.step` / `tracker.update` | 特征抽取与跟踪 |

素材为 `runs/frames/electr1` 的 60 张真实帧，检测器与感知进程分别运行，与生产
部署一致。

## 3. 结果

```
full frame()  n=59  median=  242.7ms  min=  216.3  max=  327.4
  decode     n= 60  median=  13.94ms  p90= 14.96  max= 23.55
  detector   n= 60  median= 133.63ms  p90=155.88  max=163.18
  landmarks  n= 60  median=  57.50ms  p90= 78.83  max= 94.86
  eye        n= 60  median=  22.63ms  p90= 45.27  max= 78.23
  features   n= 59  median=   0.37ms  p90=  0.58  max=  1.97
  tracker    n= 60  median=   0.02ms  p90=  0.06  max=  0.11
  accounted       median= 228.10ms   unaccounted= 14.58ms
```

判定：

1. **检测器占 55%**（133.6 / 242.7），是唯一值得动的单项；
2. MediaPipe 实测 57.5 ms，是旧记录的 3.4 倍；eye 实测 22.6 ms，是 5.7 倍。
   旧数字是单阶段空跑值，与并发时的真实成本无关；
3. `features` 与 `tracker` 合计 0.4 ms，不构成瓶颈；
4. 未归因的 14.6 ms 落在 base64 编解码、JSON 与 GIL 争用上。

## 4. 改动

`inference/live/perception_worker.py` 新增 `objects_for()` 与 `collect_detection()`：

- 检测器跑在 `ThreadPoolExecutor(max_workers=1)` 上；
- **忙时直接复用上次结果，不排队**——队列深了在检测器慢于帧率时永远排不空，
  而且每条排队条目只会让证据更旧；
- 响应的 `timestamp_ms` 保持它自己的捕获时刻，因此特征行的 `ages` 反映真实滞后，
  而不是假装这些框属于当前帧；
- 跟踪器只在收到新检测时推进一次，避免同一批框被反复关联到不同时刻；
- 首帧阻塞一次，使 slot 0 与原严格串行实现逐位一致；
- `close()` 先 `shutdown(wait=True)` 再关传输层，避免请求写进已关闭的连接；
- 30 s 死锁保护：请求卡住时立即失败，而不是让证据静默冻结到传输超时（120 s）。

## 5. 验证

### 5.1 等价性

同一段 `electr1.mp4`（1114 帧，25 Hz 网格）分别跑串行与异步，按 `window_end_ms`
去重后逐窗比对。注意服务会把最近一次窗口结果在每帧重发，所以 jsonl 的 1014 行
其实只有 **41 个不同窗口**。

| 任务 | 可用率 B→C | 检出率 B→C | 逐窗一致 | score Δ中位 | score Δ最大 |
|---|---|---|---|---|---|
| fatigue | 100% → 100% | 2.4% → 2.4% | **41/41** | 0.0000 | 0.0000 |
| phone_use | 100% → **97.6%** | 97.6% → 95.1% | 40/41 | 0.0001 | 0.0177 |
| drinking | 100% → **97.6%** | 100% → 97.6% | 40/41 | 0.0000 | 0.0007 |
| distraction | 100% → 100% | 65.9% → 68.3% | 40/41 | 0.0312 | 0.1132 |
| gaze | 63.4% → 63.4% | — | **41/41（100%）** | — | — |

差异窗口只有 2 个：

```
 5960 ms  phone_use 1.0->None, drinking 1.0->None
16960 ms  distraction 0.33->0.392
```

第一个是异步的直接代价：该窗口有一帧证据缺失，两个任务的 `available` 变 false。
第二个是阈值边界抖动。

### 5.2 性能

| 指标 | 串行 | 异步 |
|---|---|---|
| 墙钟（1114 帧） | 366.8 s | 236.5 s / 237.6 s |
| p50 | 282 ms | **172 ms** |
| 实时倍率 | 0.12× | **0.19×** |

### 5.3 中断

两次异步运行中，一次在第 979 帧因 `[WinError 10060]`（连接检测器超时）中断，
另一次 0 中断。该错误在异步化之前就出现过（见 `44c373b` 的修复背景），不是本次
引入；但异步把它的后果从“立即失败”放大成“证据静止直到传输超时”，因此补了 30 s
死锁保护。

## 6. 结论与边界

1. 异步化把单帧从 242.7 ms 降到 172 ms；是否能满足实时取决于第 7 节的定义，
   而该定义当前尚未闭合（**实时帧率目标暂缓，不下结论**）；
2. 下一段瓶颈是 MediaPipe（57.5 ms）+ eye（22.6 ms）+ 解码（13.9 ms），全在 CPU；
3. 代价已量化：`phone_use`/`drinking` 有 2.4% 窗口证据不可用，1 个窗口的
   `distraction` 判定翻转；
4. 未验证：真实 webcam 下的长时间稳定性、`drinking` 误报场景（KL-01）以外的素材、
   以及异步对 `ages` 长期贴近 81 ms 上限的影响。

## 7. 捕获帧率与 25 Hz 栅格的关系（"最低 8 帧"的修正）

### 7.1 两个概念

- **25 Hz 栅格是模型时间**：权重里 `sample_rate_hz=25`，槽位 40 ms，`FeatureExtractor`
  强制校验 `time == last+40`，不可改；
- **捕获帧率是数据供给**：可以低于 25 Hz，缺口由 `CausalClock` 用上一帧填充（零阶
  保持），被填充的槽用 `fresh` 标记其真实数据离它多远。

### 7.2 有**两道**都卡在 80 ms 的闸门，作用对象不同

| 闸门 | 位置 | 条件 | 作用 |
|---|---|---|---|
| A | `live/timeline.py` | `slot*40 - last_capture <= 80` | 该槽的像素证据算不算数 |
| B | `live/perception_worker.py` | `timestamp_ms - previous_capture > 80` | 置 `gap_pending`，下一个 head 槽带 `reset=True`，进 `EventDecoder.step` |

### 7.3 只考虑闸门 A 的实测

| 间隔 | 帧率 | 槽新鲜度 | 头采样新鲜度 |
|---|---|---|---|
| 100 ms | 10.00 Hz | 100% | 100% |
| 110 ms | 9.09 Hz | 82.2% | 69.6% |
| **120 ms** | **8.33 Hz** | **100%** | **100%** |
| **125 ms** | **8.00 Hz** | **68.0%** | **38.3%** |
| 130 ms | 7.69 Hz | 69.4% | 76.6% |
| 160 ms | 6.25 Hz | 75.0% | 76.1% |

推导（只含闸门 A）：`fresh` 要求槽偏移 ≤ 80 ms，槽位按 40 ms 离散，所以一次捕获最多
覆盖 3 个槽；因此间隔必须 **≤ 120 ms 且是 40 ms 的整数倍**，即 
$\{40, 80, 120\}$ ms（25 / 12.5 / 8.33 Hz）。

### 7.4 修正："最低 8 帧"的表述作废

早前口头把 120 ms 四舍五入成"8 Hz"并当成捕获率目标，是错的，两处：

1. **120 ms 是 8.33 Hz，不是 8 Hz**；真正的 8 Hz 是 125 ms；
2. **125 ms 恰是最坏取值**：125/40 = 3.125，在 3 槽/4 槽之间抖动，第 4 槽偏移 120 ms
   > 80，头采样新鲜度崩到 38.3%。

另外"8 Hz"曾是**头采样率**（`HEAD_OFFSETS` 每 25 槽 8 个，与捕获率无关），与捕获
帧率是两个不同的量，不应混用同一个数字。疲劳需要 32 个连续 head 槽 = **4 秒时间轴**
（在离线压缩运行时 4 秒时间轴约需 21 秒墙钟）。

### 7.5 未决：120 ms 档位是否可用

闸门 B 在间隔 **> 80 ms** 时置位。因此 120 ms 档位虽然过闸门 A，却会在每次捕获后把
`reset=True` 送进 `EventDecoder.step`。若它清空闭眼时长累积，则 120 ms 下会出现
**静默降级**：`fatigue.available` 仍为 true，但 `fatigue.detected` 趋近 0
（`closed_eye_min_ms = 1000` 永远攒不满）。

**该影响尚未验证**，需要先确认 `training/visual/action_model.py` 中 `EventDecoder.step`
的 `reset` 语义。若确认受影响，可用档位只剩 $\{40, 80\}$ ms，即最低 12.5 Hz。

**因此实时帧率目标暂缓**：不采用 120 ms，也不采用 80 ms，待上述语义确认后再定。
本条已记为 KL-11。

- `smoke_live_video.py` 新增 `--stride`，与 `--step-ms` 配合可模拟低捕获率而不把
  片段变成慢放。12.5 Hz 采样（`--stride 2 --step-ms 80`）与 25 Hz 的 41 个窗口
  比对：fatigue/phone_use/drinking 全部 41/41 一致，distraction 39/41。该档位
  间隔 80 ms 未触发闸门 B。

## 8. 并行可行性：为什么"同时跑这几个卷积"不是主要答案

问题：`detector`、`landmarks`、`eye` 三个算子能否并行，省掉串行累加？

### 8.1 依赖关系允许并行

三者都只消费 `bgr`：

```
decode_jpeg ──┬─→ detector（YOLO11s，独立进程）
              ├─→ landmarks（MediaPipe face + hands）
              └─→ eye（第二个 face 图，固定 head_roi）
                              ↓
                        features / tracker
```

`eye` 使用的是 `head_roi` 固定裁剪，不消费 `landmarks` 的输出，因此三者在数据流上
互不依赖，`decode → {三者并行} → features` 是一个成立的重排。产品代码目前把后两者
写成串行调用。

### 8.2 但感知进程只用 1.10 个核

`time.process_time()` 除以墙钟（`probe_cores` 口径，40 帧）：

| 配置 | 占用核数 |
|---|---|
| CPU 检测器（异步） | **1.10** |
| 检测器替换为即时缓存回复 | **1.10** |

结论：MediaPipe 与眼位定位在本机是**单线程**的，各占一个核即可。8 核机器表面上还有
7 个核空闲，但这是假象——检测器进程（torch 默认 8 线程，实测 8 线程最优）正在使用
它们。

### 8.3 抢占的量化

把检测器替换为"立即返回上次结果"的桩，同素材同帧数：

| 阶段 | 检测器并发时 | 无并发时 | 膨胀 | 归一化（÷decode） |
|---|---|---|---|---|
| decode | 18.25 ms | 12.73 ms | 1.4× | 1.00 |
| landmarks | **88.13 ms** | **53.66 ms** | **1.6×** | 4.22 |
| eye | 32.39 ms | 21.20 ms | 1.5× | 1.67 |
| features | 0.43 ms | 0.35 ms | — | — |
| **frame() 合计** | **145.6 ms** | **91.0 ms** | **1.6×** | 7.15 |

MediaPipe 本身只需 53.7 ms，被 YOLO 的 8 个线程挤到 88 ms。它慢的不是算子，是时间片。

### 8.4 收益上界

无并发时各阶段：decode 12.73 + landmarks 53.66 + eye 21.20 + features 0.35 = 87.9 ms，
实测 91.0 ms（11.0 Hz）。三者并行后的理论上限：

$$\max(12.73,\ 53.66,\ 21.20) + \text{调度开销} \approx 54\text{–}60\text{ ms} \Rightarrow 16\text{–}18\text{ Hz}$$

### 8.5 为什么收益会被吃掉

按核·秒估算每帧的总需求：

| 消耗方 | 核·秒/帧 |
|---|---|
| 检测器（133.6 ms × 约 8 线程） | 约 0.9 |
| 感知进程（91.0 ms × 1.10 核） | 约 0.10 |

8 核 / 1.0 核·秒 ≈ 8 帧每秒——与实测的 7–8 Hz 吻合。**这台机器的物理上限就在 8 Hz
附近，与是否并行三个算子无关。** 在检测器仍占用全部核心时把三个算子拆到三个核上，
只是把一个核的活分摊后一起被抢占。

### 8.6 结论与顺序

| 步骤 | 收益 | 前提 |
|---|---|---|
| 1. 检测器移到 GPU/NPU | 感知进程 145.6 → **91.0 ms**（1.6×） | 换执行后端 |
| 2. decode / landmarks / eye 并行 | 91.0 → **约 55–60 ms**（1.5×） | 至少 3 个空闲核 |
| 合计 | 145.6 → **约 58 ms（约 17 Hz）** | |

只做第 2 步而不做第 1 步，收益会被检测器的抢占吃掉大半。本机实测：检测器在 GPU 上
且异步时，`CameraPerception.frame()` 为 121.1 ms；该数字是否能满足实时，取决于第 7 节
的帧率定义，而该定义当前未闭合，因此不作"已达标/未达标"的结论。

### 8.7 尚未做的原因与风险

- 未实现三路并行。需要确认两个 `FaceLandmarker` 实例在不同线程并发调用是否线程安全
  （不同实例通常可以，同实例不行）；
- 本节所有数字来自同一台机器的不同时刻，背景负载有漂移（`decode_jpeg` 是固定操作，
  在三次测量中为 13.9 / 17.4 / 18.25 ms），因此跨轮比较应看归一化列或"同会话内测得的
  无并发基线"，不要直接相减；
- 未验证：真实 webcam 长稳、并行后线程间 GIL 与 XNNPACK 线程池的相互影响。
