# 训练与边缘部署方案

版本：0.3.0 · 2026-09-19 · 状态：设计基线，未部署。来源：PPT 第 9、12、13 页及用户的昇腾训练、部署便利和多平台兼容要求。

工程优先级：共享模型/数据语义、平台依赖隔离、显式backend、按目标环境实测；不以论文新颖性或复杂结构为交付要求。[关系门控](../architecture/RELATION_GATED_FUSION.md)已有CPU工程实现，但仍是待真实数据与硬件验收的候选，不替换现有基线，只有实际收益值得成本才启用。

## 1. 平台矩阵

| 场景 | 平台/环境 | 用途 | 已验证范围 |
| --- | --- | --- | --- |
| 开发与训练 | NVIDIA RTX、CUDA、PyTorch | YOLO/TCN 训练、评估、导出 | GPU 训练未实测，具体设备未确认 |
| NPU 训练 | 昇腾 910B3、Linux aarch64、Python 3.11.4、CANN 9.0.0、torch 2.7.1+cpu、torch_npu 2.7.1.post4 | 同一 YOLO/TCN 的 NPU 训练入口 | 用户的小型 Linear 前向/反向/更新通过；不是 YOLO/TCN 验证 |
| CPU 本地开发 | Windows x64、独立训练/感知环境 | 配置、契约、合成测试与实际工件加载 | 现有105项测试与三工件空白帧前向通过；新关系门控/真实视频未验证，不代表目标设备性能 |
| 目标推理部署 | NVIDIA Jetson Orin、Ubuntu/JetPack、TensorRT | 车端多专家推理、告警与应用 | 具体型号、功耗模式、JetPack 版本未定，性能未测 |

NPU 是训练平台扩展，不把它等同于 Jetson 推理或默认规划昇腾推理服务。服务器已经完成基础验证，本轮不追加硬件检查，不自动重装已工作的环境。

### 1.1 分层兼容，不复制两套模型

- 融合训练：同一PyTorch模型、loss、normalizer、checkpoint与公共循环，CUDA/torch_npu仅在对应入口初始化；无目标设备明确失败，不静默用CPU。
- 感知提取与训练可分机：在可运行YOLOX/MediaPipe的机器生成带hash特征，服务器只训练融合模型，避免为了训练强行安装整套感知依赖。
- 推理允许明确配置MediaPipe CPU + YOLOX CPU/GPU + 融合CPU/GPU。新融合NPU推理另有需求才验证；当前YOLOX检测后端明确拒绝NPU，不将训练双入口目标解释为检测已可NPU部署。
- 独立环境/requirements按OS、CPU架构和backend记录。Windows感知锁文件不是Linux/aarch64环境，CANN、CUDA和JetPack不混装成一个“通用镜像”。
- 新关系门控首阶段仅使用常见张量算子/FP32，固定小图优先；不因此宣称GPU/NPU/ONNX已兼容。

## 2. 工件流与兼容性

YOLO/TCN/关系门控：训练 checkpoint → CPU state_dict + 配置 → PyTorch FP32参考推理。ONNX是按部署需要选择的交换路径，TensorRT只在NVIDIA目标平台有实际收益时构建，不要求所有平台先导出才能运行。每个实际启用步骤记录schema、hash、工具版本、数值误差和业务变化；未生成的格式不伪造路径。导出成功不等于运行正确，更不等于达成FPS。

MediaPipe：复用官方模型工件与对应运行时，先验证目标 aarch64 的安装/构建、CPU/可用 delegate 和性能；不要求也不假定 `.task` 能直接走 PyTorch→ONNX→TensorRT 链路。部署失败需明确更换适配器/运行时并重新评估，不悄悄换特征定义。

TensorRT engine 不视为跨操作系统、硬件和版本的通用权重；默认在目标兼容环境构建，保留 ONNX 与源 checkpoint。具体能力按[TensorRT 支持矩阵](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)及锁定版本核对。FP16 为优化候选，INT8 需额外代表性校准集与精度验证。

## 3. 单机部署单元

同一版本的部署包包含：独立受监护 inference 进程、单 worker FastAPI 进程、前端静态资源、只读模型组合、可写数据库/日志目录。模型归 inference 所有，API/页面/数据库失败不阻塞本地告警。

Docker 按平台构建：RTX/CUDA 开发训练镜像、Ascend/CANN 训练镜像、Jetson 推理镜像不能混用。驱动、设备映射与 JetPack/CANN 是宿主机责任；Docker 不自动解决硬件兼容。无需把数据集打进镜像，不使用 latest 标签作为可复现环境记录。

- 模型与配置只读挂载；数据库、有限日志和明确授权的片段目录可写。
- 摄像头仅映射必要设备，非 root 运行优先；不以默认 privileged 解决权限。
- 配置摄像头标识、模型组合版本、HTTP 监听地址、Token 来源和保留策略；凭证不进镜像、Git 或日志。
- 默认仅本机访问；对局域网开放时启用 TLS/反向代理、鉴权、Origin 白名单和访问控制。
- 健康检查分进程存活、推理可用与摄像头就绪；API `/health` 返回正常不能证明检测可用。

### 3.1 Windows 桌面交付（v0.1）

v0.1 额外提供 Windows x64 桌面安装包：Electron 主进程 + PyInstaller 后端 + 预构建前端。
用户不需要安装 Python/Node，模型服务地址与专用 Token 在构建时完全内置；模型服务仍是
外部依赖，桌面包不包含权重、CANN/NPU 运行时。

- 后端只监听 `127.0.0.1`随机端口，本地管理 Token 每次启动随机生成；
- 模型服务 Token 写入用户数据目录供后端读取，不进入渲染进程；
- 数据目录为 `%APPDATA%\DriveGuardAI`，卸载默认保留；
- 启动时探测 `/api/live/health`，不可达时明确提示并允许重试/退出；
- 完全内置 Token 的代价是可能被提取，只应使用专用、可轮换、权限受限的 Token。

构建与验收见 [Windows 桌面版](DESKTOP_APP.md)，发布范围见

## 4. 采集、调度与性能

开发可使用 OpenCV 摄像头读取；Jetson 优先评估 GStreamer 采集/硬件解码路径，选择必须由实际驱动与测量支撑。采集记录 UTC 用于审计、单调时钟用于时长；排队有上限，实时处理优先新帧。

PPT 的持续 `≥25 FPS` 是完整管线目标，不是 TCN 独立 benchmark。报告摄像头输入、实际处理帧、各专家有效更新率、丢帧比例、预览开启状态以及 CPU/GPU/内存/温度/功耗。高频重复旧检测结果不能冒充 25 FPS 有效感知。

分别测量：采集到风险快照的 P50/P95、行为起点到有效告警的检测延迟、3–5 秒窗口的预热时间、WS 展示延迟、预览延迟。不存在未经测量的统一“毫秒级完成”承诺。优化顺序为定位瓶颈→调整分辨率/专家频率→导出加速→重跑精度与事件评估。

## 5. 存储与容量

训练服务器总预算 200 GB：下载/解压峰值、已选视频、特征缓存、checkpoint、日志、环境及安全余量一起计入。当前下载未完成，本轮不改下载任务；后续处理前核对实际剩余空间，不声称四个分片一定装得下。

不全量抽帧，不复制滑动窗口；录制级缓存按需生成，保留与清理由清单驱动并先确认可重建性。best/last 与公开工件保留，中间 checkpoint 可设置数量上限。训练数据与环境目录继续 Git ignore。

部署端不含 DMD 原视频；SQLite/WAL、日志、可选片段各设容量/保留限制。磁盘不足停止非必要片段写入并报告存储降级，本地推理与告警尽量继续；不自动删除未授权原始数据。

## 6. 升级、回滚与恢复

1. 离线准备兼容组合 manifest，核对每个权重、提取 profile、normalizer 与规则的校验和。
2. 在候选环境加载并回放；记录PyTorch参考与实际启用后端的误差及可用任务表现，未训练/未验证任务保持不可用。
3. 保留前一组合与一致的配置；会话边界切换新组合，重置窗口和时序状态，不混合新旧特征。
4. 迁移数据库前备份并验证可恢复；失败时恢复兼容数据库和旧组合，不能仅退权重。
5. 重启 API 后重建 WS、从数据库恢复历史；推理进程重启建立新会话，预热期显示不可用。

告警本地独立，断网不影响核心闭环；缓存不是无损持久队列，数据库/API 故障期的事件缺口须显式记录。长稳验收包含摄像头拔插、API 重启、磁盘/内存压力、慢 WS 客户端、预览开启和网络断开。

## 7. 实施交付清单

后续交付平台 requirements/锁定环境、Dockerfile/启动配置、迁移、运行手册、模型 manifest、校验和与 benchmark 报告；当前这些仍是待实现项。正式训练权重的公开与来源许可见[训练职责约定](../training/TRAINING_CHARTER.md)，不同平台的完成状态分别记录。

关系门控组合另含模型类型、group_profile/质量策略、任务已验证支持组合。保留已验证的基线组合，升级/回退同步恢复全部相关工件并清空窗口；不因模型失败自动切换backend。新融合模型和完整系统尚未部署，本轮没有修改服务器、依赖或数据库。
