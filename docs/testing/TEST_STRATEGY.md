# DriveGuard AI 测试策略

## 1. 目标

版本：0.2.0 · 2026-09-18。定义 PPT 全方案验收；除明确记录的 TCN 工程测试外，下述场景仍为计划测试。

测试用于证明需求、模型行为、数据契约和运行性能达到可接受水平，而不只验证代码可以启动。当前全量105项unittest通过：TCN训练29项、感知桥接33项、本地专家运行时43项，见[TCN记录](../experiments/20260918-temporal-engineering-smoke.md)、[桥接记录](../experiments/20260918-perception-bridge.md)和[运行时记录](../experiments/20260918-expert-runtime.md)。这些测试仍使用外部模型/解码API替身；2026-09-19另在torch2.7.1+cpu新环境执行105项测试，并用三个真实工件完成两帧空白图前向，见[准备记录](../training/PERCEPTION_SETUP.md)。真实视频、DMD、GPU/NPU、应用与完整系统端到端测试尚未进行。

## 3. 数据集与模型评估

### 3.1 数据切分

- DMD 必须按 `driver_subject_id` 划分训练、验证、测试集。
- 三个集合的主体交集必须为空；摄像头视角与同一段视频衍生帧不得跨集合泄漏。
- 切分清单应版本化，并记录数据集版本、随机种子和过滤规则。

### 3.1.1 四任务 TCN 设计验证

四任务设计补充（REQ-012，训练工程测试已实现）：按 [TCN 模型设计](../training/MODEL_DESIGN.md)检查输入/输出形状、因果性与参数量；验证输入 mask 与 label_mask 独立、未知标签无直接分类损失梯度、全未知 batch 不更新但保留标签覆盖计数、全未知 epoch 失败、验证损失不随 batch 分组变化。归一化仅使用训练主体的有效时间槽；主体划分覆盖全部子集和视角；未训练任务在报告中标记不可评估。业务推理中的任务可用性适配仍待实现。用户提供的 NPU Linear 测试不代表完整 TCN 验证，本轮不追加远程硬件测试。

### 3.1.2 轻量关系门控与跨平台验证

设计见[关系门控](../architecture/RELATION_GATED_FUSION.md)，对应REQ-011/013新增场景。原105项历史测试不包含该新网络；本轮新增关系门控数据/模型/训练/导出测试及独立CPU合成工具，覆盖前述CPU工程路径，见[运行指南](../training/RELATION_RUNBOOK.md)。下列平台、导出优化、真实回放与业务回退仍按后续阶段验证，不能把CPU测试当作全部完成。最低验证集：

- 契约：19字段分组覆盖/顺序、v1/v2拒绝混用、年龄非负与未知、quality/normalizer/hash一致。
- 缺失：分别屏蔽Face/Hands/Objects并核对派生字段；成功空检测与推理失败不混同；持续时长不跨失效拼接。
- 数值：全有效、单流、全无效和混合batch；权重有限、无效流严格零、可用流归一；无输入分类头bias不对外形成有效结果。
- 因果与训练：未来输入不影响过去；未知标签无对应分类损失，零有效输入样本不更新但计数；CPU保存/恢复与新旧模型类型检查。
- 平台：固定输入/同一初始化权重分别做CPU/CUDA/NPU前后向和加载；FP32初始logit容差atol=1e-4、rtol=1e-3，mask/可用性完全一致。不要求不同设备独立训练轨迹逐位一致。缺硬件记未验证，不能用CPU或基础Linear替代。
- 导出：只验证实际选用后端；固定B=1/T=100起步，图内数值与图外质量/可用性适配一起检查。ONNX通过不能替代目标TensorRT/MediaPipe验证。
- 回放：相同主体划分和证据下比较38通道基线/门控候选；额外质量输入需给基线同样证据或明确不作为结构优势。以误报、漏报、可用率和总延迟判断是否启用，不强制多种子论文式实验。
- 拒答偏差：同时报告不可用时长及其中的已标注危险事件漏检；未验证任务/缺失组合不记为已支持。模拟特征缺失与真实遮挡分别报告。
- 回退：恢复完整旧组合，校验模型/profile/backend并清空窗口；不擅自换设备，不改变API/风险枚举。

### 3.2 指标

按[完整多专家设计](../architecture/MULTI_EXPERT_DESIGN.md)分层报告：YOLO 的逐类 mAP50/mAP50-95 与检测 P/R；面部/手部特征的有效覆盖率、关联反例与延迟；TCN 的四任务 masked P/R/F1；完整管线的事件指标与 FPS。DMD 行为标签不能作为 bbox 检测真值。没有标注支持的指标记 N/A，不用准确率替代危险行为召回。

| 指标 | 用途 |
| --- | --- |
| Precision / Recall / F1 | 分类质量，优先关注危险行为 Recall |
| False Alarm / Hour | 实际驾驶体验与告警疲劳 |
| Detection Delay | 行为出现到首次有效告警的延迟 |
| FPS / P50/P95 latency | 实时性和尾延迟 |
| Calibration error | 概率是否可用于风险融合 |
| Missing/occlusion slices | 低光、遮挡、眼镜、姿态变化鲁棒性 |

报告必须注明硬件、输入分辨率、窗口长度、模型版本、运行时和精度模式；不同条件的数字不得直接横向比较。

事件评估须预先固定事件合并间隔、最短持续时间与匹配容差，同类型一对一匹配真值和预测事件。危险行为 Recall=匹配真值事件数/已知真值事件数；False Alarm/Hour=未匹配告警事件数/有效且标注充分的监测小时数，同时记录排除的未知/掉线时长；Detection Delay=匹配事件首次有效告警时间−真值起点，报告分布与漏检数，漏检不填零延迟。仅有窗口标签时不报告这些事件指标。

优先比较现有38通道TCN与轻量关系门控，保持主体划分、感知工件与训练预算一致，记录收益和额外算力。旧24通道、单帧/规则等对照按排错需要追加，不作为论文式强制消融门禁。PPT 示例概率与“毫秒级”措辞不作实验结果。

## 4. 核心测试场景

### 4.1 正常与边界

- 空画面、无人脸、单帧、窗口未填满、时间戳倒退和重复帧。
- 正常眨眼、持续闭眼、连续打哈欠、短暂低头和持续低头。
- 手机只在背景出现、手机靠近驾驶员但未交互、持续手机交互。
- 副驾驶持手机、手机支架、杯子静置、手持杯但未饮水；手被遮挡时 mask=0，不能判定确定未交互。
- 仅眼球偏移但头姿不变、正常查看后视镜：披露首版 gaze 能力边界，不以头姿模拟精确 gaze 标签。
- 多风险同时出现、单专家缺失、所有关键专家不可用。
- 风险在阈值上下抖动、升级、恢复、冷却和重复告警抑制。

### 4.2 数据库

- 空库、单条事件、10 万条事件分页、时间范围边界和稳定排序。
- 活动事件创建/更新/结束、服务重启后活动事件恢复。
- 配置乐观锁成功与冲突、非法 JSON、事务回滚。
- 数据库锁定或写入失败时，本地告警仍继续且错误可观测。

### 4.3 REST/WebSocket

- 每个端点至少覆盖成功、鉴权失败、校验失败和资源不存在/冲突中适用的场景。
- `page_size=0/1/100/101`、反向时间范围、非法 UUID 和未知枚举。
- WebSocket 初始完整快照、序列单调性、心跳、慢客户端、断线重连和 Token 失效。
- FastAPI 生成的 OpenAPI 与 `docs/api/openapi.yaml` 进行结构差异检查。
- API-009 无有效结论返回 503；risk_scores 缺失任务不补零；新会话序列重置并清理旧曲线。
- API-010 覆盖默认关闭、鉴权、权限、200 MJPEG/禁止缓存、摄像头故障、管理员关闭、取消清理和慢消费者。200 之后只终止流，不插入 JSON 错误。
- runtime 的 mediapipe/python 在数据库、Pydantic/OpenAPI 与 TypeScript 一致；完整组合 manifest 的工件与 schema 不一致须拒绝激活。

### 4.4 隐私和安全

- 默认配置运行后，数据库、日志和文件系统中不存在原始视频片段。
- 开启预览后仍不落盘；Token 不在预览 URL/日志；关闭预览释放连接但推理保持运行。
- 路径穿越、超长输入、未知配置键和越权配置修改被拒绝。
- 错误响应不包含堆栈、Token、绝对模型路径或数据库路径。

## 6. 性能测试

### 6.1 基准矩阵

- 设备：开发 RTX GPU、目标 Jetson Orin 型号。
- 运行时：PyTorch、ONNX Runtime、TensorRT FP16。
- MediaPipe 自身运行时与 face/hand 工件单独列出；不能将它默认计入 TensorRT 转换成功率。
- 输入：至少两种目标分辨率和目标摄像头帧率。
- 工况：稳定画面、多人/遮挡、持续一小时和资源压力。

### 6.2 最小报告字段

```text
commit, model_bundle_version, device, power_mode, runtime, precision,
resolution, input_fps, processed_fps, latency_p50_ms, latency_p95_ms,
gpu_memory_mb, cpu_percent, dropped_frame_rate, duration_minutes
```

25 FPS 是完整管线目标；如果未达到，应报告瓶颈与实测差距，不得把短时峰值或重复旧检测当作持续性能。分别记录输入 FPS、处理 FPS、专家有效更新率、丢帧率、WS/预览频率、预览开关及功耗/温度。实际平台和部署条件见[部署方案](../deployment/DEPLOYMENT_DESIGN.md)。

## 8. CI 阶段建议

1. 快速检查：格式、lint、类型、单元测试、OpenAPI/YAML 解析。
2. 集成检查：SQLite migration、Repository、API 与 WebSocket 测试。
3. 模型检查：固定小样本回归，不在每次提交运行完整训练。
4. Nightly/候选发布：完整回放集、性能、长稳、隐私和目标设备测试。

## 9. 通过标准与证据

训练工程新增检查（REQ-011，负责人 shadow）：配置类型与范围、外置路径、训练/验证/测试主体交集、设备不可用时显式失败、checkpoint CPU 可加载、resume 与训练配置一致。双入口共享测试；真实 GPU 与昇腾 NPU 运行各留设备和环境记录。合成 smoke 只能证明代码闭环，不能作为模型正式跑分。预算实验顺序见[训练职责约定](../training/TRAINING_CHARTER.md)。

- 新增或修改 Requirement 时，至少有一个可执行或明确待实现的测试映射。
- 代码合并前相关自动化测试通过；无法自动化的验收需附复现步骤、环境和结果。
- 模型或阈值变更必须附相同数据切分和硬件口径下的前后对比。
- 已知失败不得隐藏，应记录影响、临时处理和后续验证入口。
